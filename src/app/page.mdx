## Why Keploy? {/* anchor: why-keploy */}

<span id="why-keploy" style={{ scrollMarginTop: "5rem", display: "block", marginTop: "-5rem", paddingTop: "5rem", visibility: "hidden", pointerEvents: "none" }} aria-hidden="true" />

<Callout type="tip" title="The Real Problem">
  Writing integration tests for API endpoints is expensive. You need fixtures, mocks, DB state, and ongoing maintenance. Most teams skip it — and find bugs in production instead.
</Callout>

Keploy takes a fundamentally different approach. Instead of writing tests upfront, it **observes your running application** and turns real traffic into reusable, deterministic test cases automatically.

<BeforeAfter />

<InfoCardGrid>
  <InfoCard title="What Keploy captures" icon="📡">
    HTTP request method, path, headers, and body — the exact shape of each real API call made against your server.
  </InfoCard>
  <InfoCard title="What Keploy stores" icon="💾">
    A YAML snapshot of the request, the response your app produced, and the state of all external dependencies.
  </InfoCard>
  <InfoCard title="What Keploy replays" icon="▶️">
    The same requests, with mocked dependencies — then asserts the responses match the recorded snapshots.
  </InfoCard>
</InfoCardGrid>

**The key insight:** Keploy doesn't mock your tests — it records reality. Test cases are grounded in actual behavior, not assumptions.

This is where things get interesting. Instead of running your app directly, you run it **under Keploy's supervision**.

<Step number="1" title="Start your app in record mode">

<CodeBlock language="bash">
{`keploy record -c "./mux-mysql"`}
</CodeBlock>

<Callout type="tip" title="What does keploy record do?">
  It starts your application as a child process, then intercepts all network traffic — both inbound HTTP requests and outbound calls to MySQL. Every interaction is recorded as a YAML file in <code>keploy/</code>.
</Callout>

## What Keploy Captured {/* anchor: what-keploy-captured */}

<span id="what-keploy-captured" style={{ scrollMarginTop: "5rem", display: "block", marginTop: "-5rem", paddingTop: "5rem", visibility: "hidden", pointerEvents: "none" }} aria-hidden="true" />

Let's look at what Keploy wrote to disk — the `get-all-1.yaml` test case:

<CodeBlock language="yaml" filename="keploy/test-set-0/tests/get-all-1.yaml">
{`version: api.keploy.io/v1beta1
kind: Http
name: get-all-1
spec:
  metadata: {}
  req:
    method: GET
    proto_major: 1
    proto_minor: 1
    url: http://localhost:8080/links
    header:
      User-Agent: curl/7.88.1
      Accept: "*/*"
    body: ""
  resp:
    status_code: 200
    header:
      Content-Type: application/json
    body: |
      [{"id":1,"url":"https://keploy.io","custom":"keploy"}]
  objects: []
  assertions:
    noise:
      - header.Date`}
</CodeBlock>

<Callout type="info" title="What You're Looking At">
  The <code>req</code> block is what Keploy replays. The <code>resp</code> block is the expected output your app must match. The <code>assertions.noise</code> field tells Keploy to ignore <code>header.Date</code> — it changes on every request and would cause false failures.
</Callout>

And the `mappings.yaml` that stubs the database:

<CodeBlock language="yaml" filename="keploy/test-set-0/mappings.yaml">
{`version: api.keploy.io/v1beta1
kind: Mapping
name: mappings
spec:
  deps:
    - name: mysql
      type: SQL
      meta:
        driver: mysql
        host: localhost
        port: "3306"
        user: root
        dbName: keploy`}
</CodeBlock>

## Understanding the Generated Tests {/* anchor: understanding-the-tests */}

<span id="understanding-the-tests" style={{ scrollMarginTop: "5rem", display: "block", marginTop: "-5rem", paddingTop: "5rem", visibility: "hidden", pointerEvents: "none" }} aria-hidden="true" />

<Callout type="tip" title="Why Two Test Sets?">
  I ran two recording sessions — hence <code>test-set-0</code> and <code>test-set-1</code>. Each <code>keploy record</code> run creates a new test set. This lets you capture different application states in separate baselines.
</Callout>

Here are all three captured test types — expand each to see the recorded data:

<TestCaseCards />

### What are the mappings for?

The `mappings.yaml` records the state of external dependencies at recording time. During test replay, **Keploy does not hit the real database**. It serves mocked responses from the recorded mappings.

This makes tests deterministic: they pass regardless of whether your database has the same data or even exists.

<Callout type="tip" title="This Is the Real Superpower">
  Keploy eliminates fixture management entirely. The mappings handle database state automatically — no seeding, no resetting, no manual state setup.
</Callout>

## Replay the Tests {/* anchor: replay-the-tests */}

<span id="replay-the-tests" style={{ scrollMarginTop: "5rem", display: "block", marginTop: "-5rem", paddingTop: "5rem", visibility: "hidden", pointerEvents: "none" }} aria-hidden="true" />

<Step number="1" title="Run keploy test">

<CodeBlock language="bash">
{`keploy test -c "./mux-mysql" --delay 10`}
</CodeBlock>

The `--delay 10` flag gives your app 10 seconds to start before Keploy begins replaying requests. Adjust if your app takes longer.

<ExpectedOutput lines={[
  "… Starting ./mux-mysql",
  "… Replaying test-set-0 (3 tests)",
  "… Replaying test-set-1 (3 tests)",
  "✓ 6/6 tests passed",
]} label="Representative Keploy output" />

</Step>

<Step number="2" title="What happens during replay" last={true}>

Keploy:
1. Starts your Go application as a subprocess
2. Replays each recorded HTTP request from every test set, in order
3. Compares the actual response against the recorded snapshot
4. Reports pass or fail per test

No test runner config. No fixtures to seed. No manual assertions to write.

<Callout type="info" title="What Keploy Asserts">
  By default: HTTP status code, response body, and headers — minus the noise list. Body comparison is structural; minor formatting differences don't cause failures.
</Callout>

</Step>

## The 6/6 Result {/* anchor: the-6-6-result */}

<span id="the-6-6-result" style={{ scrollMarginTop: "5rem", display: "block", marginTop: "-5rem", paddingTop: "5rem", visibility: "hidden", pointerEvents: "none" }} aria-hidden="true" />

<TestResult />

Every test passed. Both sessions. All three endpoint types — create, list, and fetch-by-id.

### What "passed" means

A test passes when:
- The HTTP status code matches the recorded status code
- The response body matches the recorded body (excluding noisy fields)
- All mocked dependency interactions completed as expected

<Callout type="success" title="6/6 — Regression Safety Established">
  A 6/6 pass means your application's behavior matches exactly what was recorded. Change a response field incorrectly, break a handler, or introduce a DB regression — the corresponding test will fail and tell you exactly which endpoint broke.
</Callout>

## What I Learned {/* anchor: what-i-learned */}

<span id="what-i-learned" style={{ scrollMarginTop: "5rem", display: "block", marginTop: "-5rem", paddingTop: "5rem", visibility: "hidden", pointerEvents: "none" }} aria-hidden="true" />

Running this quickstart genuinely changed how I think about integration testing. Honest takeaways:

<InfoCardGrid>
  <InfoCard title="Tests from reality, not assumptions" icon="💡">
    Writing tests based on what you <em>think</em> the API does is risky. Recording what it <em>actually</em> does is grounded in truth. Keploy makes this distinction automatic.
  </InfoCard>
  <InfoCard title="Mappings solve the hard problem" icon="🗺️">
    Managing database state in integration tests is notoriously painful. The mappings system sidesteps it entirely — and it works.
  </InfoCard>
  <InfoCard title="CLI version matters" icon="⚙️">
    Always run <code>keploy --help</code> when a command fails. The CLI evolves fast and docs sometimes lag. Work from what the installed CLI actually exposes.
  </InfoCard>
  <InfoCard title="Test sets = isolated states" icon="📁">
    Each <code>keploy record</code> run is a new test set. You can capture different states — empty DB, populated DB, error paths — as separate baselines.
  </InfoCard>
</InfoCardGrid>

The broader lesson: Keploy isn't magic, but it's genuinely useful. It's best for teams with working APIs and weak test coverage — it gives you a solid regression baseline quickly, grounded in real behavior.
