## Why Keploy? {/* anchor: why-keploy */}

<span id="why-keploy" style={{ scrollMarginTop: "5rem", display: "block", marginTop: "-5rem", paddingTop: "5rem", visibility: "hidden", pointerEvents: "none" }} aria-hidden="true" />

<Callout type="tip" title="The Problem It Addresses">
  Writing integration tests for API endpoints is expensive. You need fixtures, mocks, DB state, and ongoing maintenance. Most teams skip it — and find bugs in production instead.
</Callout>

Instead of writing tests upfront, Keploy **observes a running application** and turns real traffic into reusable, deterministic test cases.

<BeforeAfter />

<InfoCardGrid>
  <InfoCard title="What Keploy captures">
    HTTP request method, path, headers, and body — the exact shape of each real API call made against your server.
  </InfoCard>
  <InfoCard title="What Keploy stores">
    A YAML snapshot of the request, the response your app produced, and the state of all external dependencies.
  </InfoCard>
  <InfoCard title="What Keploy replays">
    The same requests, with mocked dependencies — then asserts the responses match the recorded snapshots.
  </InfoCard>
</InfoCardGrid>

Keploy records the application's actual request and dependency behavior, then replays that behavior during testing. Test cases are grounded in observed traffic rather than assumptions about what the API should do.

## Run the Application {/* anchor: run-the-application */}

<span id="run-the-application" style={{ scrollMarginTop: "5rem", display: "block", marginTop: "-5rem", paddingTop: "5rem", visibility: "hidden", pointerEvents: "none" }} aria-hidden="true" />

<Step number="1" title="Clone the samples repository">

<CodeBlock language="bash">
{`git clone https://github.com/keploy/samples-go.git
cd samples-go/mux-mysql`}
</CodeBlock>

<ExpectedOutput lines={[
  "Cloning into 'samples-go'...",
  "Resolving deltas: 100% (...)...",
  "# cd samples-go/mux-mysql",
]} />

The `mux-mysql` app is a URL shortener with three endpoints — exactly the three test cases we'll record. The sample's own repository doesn't ship a `docker-compose.yml`; it starts MySQL with a plain `docker run`, so that's what this walkthrough uses too.

</Step>

<Step number="2" title="Start MySQL">

<CodeBlock language="bash">
{`docker run -p 3306:3306 --rm --name mysql \\
  -e MYSQL_ROOT_PASSWORD=my-secret-pw \\
  -d mysql:latest`}
</CodeBlock>

<Callout type="tip" title="Why a container for MySQL?">
  The app needs MySQL reachable at a specific host/port without a manual install. Keploy will capture the exact DB queries the app makes against it — and replay them as mocked responses later, so this container never needs to be touched during replay.
</Callout>

<CodeBlock language="bash">
{`# Wait for MySQL to finish initializing
docker logs -f mysql`}
</CodeBlock>

<ExpectedOutput lines={[
  "… [MySQL initializing]",
  "… ready for connections",
  "# Press Ctrl+C to stop following logs",
]} label="Representative output" />

<Callout type="info" title="Connection string">
  The app reads its MySQL connection details from a single environment variable — no fallback, it exits if this is unset.
</Callout>

<CodeBlock language="bash">
{`export ConnectionString="root:my-secret-pw@tcp(localhost:3306)/mysql"`}
</CodeBlock>

</Step>

<Step number="3" title="Build the Go binary">

<CodeBlock language="bash">
{`go mod tidy
go build -o mux-mysql .`}
</CodeBlock>

<ExpectedOutput lines={[
  "# go mod tidy downloads missing modules",
  "# go build produces the ./mux-mysql binary",
  "# No output on success — the binary is ready",
]} label="Expected (no output on success)" />

A successful build confirms all imports resolve before adding Keploy to the mix. (The sample's own instructions build to `./main`; this walkthrough just names the binary `mux-mysql` — either name works with `go build -o`.)

</Step>

<Step number="4" title="Understand the three routes" last={true}>

<CodeBlock language="go">
{`// main.go — three routes, three test cases
router.HandleFunc("/create", controller.CreateLink(store)).Methods("POST")
router.HandleFunc("/all", controller.GetAllLinksFromWebsite(store)).Methods("GET")
router.HandleFunc("/links/{id}", controller.RedirectUser(store)).Methods("GET")`}
</CodeBlock>

Each handler talks to MySQL. `RedirectUser` is worth noting — it doesn't return JSON, it looks up the stored URL and issues an HTTP redirect to it. Keploy sits between the app and the database, capturing both the HTTP and the DB interaction regardless of which shape the response takes.

</Step>

## Start Recording {/* anchor: start-recording */}

<span id="start-recording" style={{ scrollMarginTop: "5rem", display: "block", marginTop: "-5rem", paddingTop: "5rem", visibility: "hidden", pointerEvents: "none" }} aria-hidden="true" />

This is where things get interesting. Instead of running your app directly, you run it **under Keploy's supervision**.

<Step number="1" title="Start your app in record mode">

<CodeBlock language="bash">
{`keploy record -c "./mux-mysql"`}
</CodeBlock>

<Callout type="tip" title="What does keploy record do?">
  It starts your application as a child process, then intercepts all network traffic — both inbound HTTP requests and outbound calls to MySQL. Every interaction is recorded as a YAML file in <code>keploy/</code>.
</Callout>

<ExpectedOutput lines={[
  "… Keploy starts your app as a subprocess",
  "… Traffic interception active on port 8080",
  "# Make your API requests now",
]} label="Representative output" />

</Step>

<Step number="2" title="Send real API requests">

With the app recording, use curl to make real API calls. Each request becomes a test case.

<CodeBlock language="bash">
{`# 1 — Create a new link
curl -s -X POST http://localhost:8080/create \
  -H "Content-Type: application/json" \
  -d '{"link": "https://keploy.io"}'`}
</CodeBlock>

<ExpectedOutput lines={[
  '{"message":"Converted","link":"http://localhost:8080/links/1","status":true}',
  "# Keploy records this request in the background",
]} label="Representative response — matches the app's response shape" />

<CodeBlock language="bash">
{`# 2 — Fetch all links
curl -s http://localhost:8080/all`}
</CodeBlock>

<ExpectedOutput lines={[
  '{"message":[{"id":"1","website":"https://keploy.io"}],"status":true}',
  "# Keploy records this request in the background",
]} label="Representative response — matches the app's response shape" />

<CodeBlock language="bash">
{`# 3 — Fetch a specific link by ID
curl -s -i http://localhost:8080/links/1`}
</CodeBlock>

<ExpectedOutput lines={[
  "HTTP/1.1 307 Temporary Redirect",
  "Location: https://keploy.io",
  "# This route redirects rather than returning JSON — the -i flag shows the headers",
]} label="Representative response — matches the app's response shape" />

<Callout type="warning" title="Not a JSON endpoint">
  Unlike the other two routes, <code>GET /links/{"{"}id{"}"}</code> is a redirect handler. It responds with <code>307 Temporary Redirect</code> and a <code>Location</code> header pointing at the original URL — there's no JSON body to inspect. Keploy still records this correctly; the generated test case just asserts the status code and header instead of a body.
</Callout>

</Step>

<Step number="3" title="Stop the recording" last={true}>

Press `Ctrl+C` to stop. Keploy writes the session to disk.

<Callout type="success" title="Recording Complete">
  After stopping, you'll find a new <code>keploy/test-set-0/</code> folder with 3 test files and a <code>mappings.yaml</code>.
</Callout>

</Step>

## What Keploy Captured {/* anchor: what-keploy-captured */}

<span id="what-keploy-captured" style={{ scrollMarginTop: "5rem", display: "block", marginTop: "-5rem", paddingTop: "5rem", visibility: "hidden", pointerEvents: "none" }} aria-hidden="true" />

Here's the shape of what Keploy writes to disk for the `get-all-1.yaml` test case. The structure below (top-level keys, `req`/`resp` split, `assertions.noise`) reflects Keploy's documented test format — treat the exact field layout as **representative**, since a generated file can vary slightly by Keploy version:

<CodeBlock language="yaml" filename="keploy/test-set-0/tests/get-all-1.yaml">
{`version: api.keploy.io/v1beta1
kind: Http
name: get-all-1
spec:
  metadata: {}
  req:
    method: GET
    proto_major: 1
    proto_minor: 1
    url: http://localhost:8080/all
    header:
      User-Agent: curl/7.88.1
      Accept: "*/*"
    body: ""
  resp:
    status_code: 200
    header:
      Content-Type: application/json
    body: |
      {"message":[{"id":"1","website":"https://keploy.io"}],"status":true}
  objects: []
  assertions:
    noise:
      - header.Date`}
</CodeBlock>

<Callout type="info" title="What You're Looking At">
  The <code>req</code> block is what Keploy replays. The <code>resp</code> block is the expected output your app must match. The <code>assertions.noise</code> field tells Keploy to ignore <code>header.Date</code> — it changes on every request and would cause false failures.
</Callout>

And the `mappings.yaml` that stubs the database — again, representative of the structure rather than a guaranteed byte-for-byte schema:

<CodeBlock language="yaml" filename="keploy/test-set-0/mappings.yaml">
{`version: api.keploy.io/v1beta1
kind: Mapping
name: mappings
spec:
  deps:
    - name: mysql
      type: SQL
      meta:
        driver: mysql
        host: localhost
        port: "3306"
        user: root
        dbName: mysql`}
</CodeBlock>

## Understanding the Generated Tests {/* anchor: understanding-the-tests */}

<span id="understanding-the-tests" style={{ scrollMarginTop: "5rem", display: "block", marginTop: "-5rem", paddingTop: "5rem", visibility: "hidden", pointerEvents: "none" }} aria-hidden="true" />

<Callout type="tip" title="Why Two Test Sets?">
  I ran two recording sessions — hence <code>test-set-0</code> and <code>test-set-1</code>. Each <code>keploy record</code> run creates a new test set. This lets you capture different application states in separate baselines.
</Callout>

Here are all three captured test types — expand each to see the recorded data:

<TestCaseCards />

### What are the mappings for?

The `mappings.yaml` records the state of external dependencies at recording time. During test replay, **Keploy does not hit the real database**. It serves mocked responses from the recorded mappings.

This makes tests deterministic: they pass regardless of whether your database has the same data or even exists.

<Callout type="tip" title="Why mappings matter">
  This is what removes fixture management from the test loop: no seeding, no resetting, no manual state setup. The mapping file, not your database, is the source of truth during replay.
</Callout>

## Replay the Tests {/* anchor: replay-the-tests */}

<span id="replay-the-tests" style={{ scrollMarginTop: "5rem", display: "block", marginTop: "-5rem", paddingTop: "5rem", visibility: "hidden", pointerEvents: "none" }} aria-hidden="true" />

<Step number="1" title="Run keploy test">

<CodeBlock language="bash">
{`keploy test -c "./mux-mysql" --delay 10`}
</CodeBlock>

The `--delay 10` flag gives your app 10 seconds to start before Keploy begins replaying requests. Adjust if your app takes longer.

<ExpectedOutput lines={[
  "… Starting ./mux-mysql",
  "… Replaying test-set-0 (3 tests)",
  "… Replaying test-set-1 (3 tests)",
  "6/6 tests passed",
]} label="Representative Keploy output" />

</Step>

<Step number="2" title="What happens during replay" last={true}>

Keploy:
1. Starts your Go application as a subprocess
2. Replays each recorded HTTP request from every test set, in order
3. Compares the actual response against the recorded snapshot
4. Reports pass or fail per test

No test runner config. No fixtures to seed. No manual assertions to write.

<Callout type="info" title="What Keploy Asserts">
  By default: HTTP status code, response body, and headers — minus the noise list. Body comparison is structural; minor formatting differences don't cause failures.
</Callout>

</Step>

<span id="the-6-6-result" style={{ scrollMarginTop: "5rem", display: "block", marginTop: "-5rem", paddingTop: "5rem", visibility: "hidden", pointerEvents: "none" }} aria-hidden="true" />

<TestResult />

Every test passed. Both sessions. All three endpoint types — create, list, and fetch-by-id.

### What "passed" means

A test passes when:
- The HTTP status code matches the recorded status code
- The response body matches the recorded body (excluding noisy fields)
- All mocked dependency interactions completed as expected

<Callout type="success" title="6/6 — Regression Safety Established">
  A 6/6 pass means your application's behavior matches exactly what was recorded. Change a response field incorrectly, break a handler, or introduce a DB regression — the corresponding test will fail and tell you exactly which endpoint broke.
</Callout>

## What I Learned {/* anchor: what-i-learned */}

<span id="what-i-learned" style={{ scrollMarginTop: "5rem", display: "block", marginTop: "-5rem", paddingTop: "5rem", visibility: "hidden", pointerEvents: "none" }} aria-hidden="true" />

Notes from actually running this end to end:

<InfoCardGrid>
  <InfoCard title="Tests reflect observed behavior, not assumed behavior">
    Writing tests based on what you think the API does is a guess. Recording what it actually does removes that guesswork — the assertions come from a real response, not a spec.
  </InfoCard>
  <InfoCard title="Mappings replace fixture management">
    Managing database state across test runs is normally the painful part of integration testing. Here, the mapping file stands in for the database at replay time, so there's nothing to seed or reset.
  </InfoCard>
  <InfoCard title="Check --help against the installed CLI version">
    One command from the docs didn't exist in 3.8.47. Running <code>keploy --help</code> settled it immediately — worth doing first whenever a command fails, since CLI and docs can drift.
  </InfoCard>
  <InfoCard title="Each recording is an isolated test set">
    Every <code>keploy record</code> run creates a new test set. That means you can capture different states — empty DB, populated DB, error paths — as separate baselines without them interfering.
  </InfoCard>
</InfoCardGrid>

Where this fits: it's a fast way to get regression coverage on an API that already works, without hand-writing fixtures. It doesn't replace thinking about edge cases or writing tests for behavior that hasn't happened yet — it only knows what it's seen recorded.
